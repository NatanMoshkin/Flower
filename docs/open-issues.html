#1 — sTime breaks any ADS sum-up read it joins Blocking a feature

Owner: engineering · Blocks: showing the PLC's own timestamp in FlowerPyHmi · Found 2026-07-27

Symptom. GVL_Log.aRecent[i].sTime reads correctly one symbol at a time, but fails every batched read it is included in:

sTime:    batch FAILED -> RuntimeError: Insufficient data (expected 827 bytes, 798 were read)
sTime:    read_by_name  = '16:47:16'
sSevText: batch OK, sample = 'INFO'

Why it matters. read_list_by_name resolves symbol info for every name in the transaction, so one malformed entry fails the whole sum-up — that would take down the entire ~220-symbol poll cycle in FlowerPyHmi, not just the timestamp column. This is why sTime is deliberately absent from LOG_ENTRY_FIELDS.

Likely cause. The panel's ADS symbol table is stale for that field; it looks as though sTime went in via an Online Change rather than a full Activate.

How to resolve. Full Activate Configuration on the panel (not Online Change), then re-run the probe. Only add sTime to LOG_ENTRY_FIELDS once a 20-symbol batch of it succeeds. Until then FlowerPyHmi stamps its own arrival time, which is why all rows loaded in one poll share a timestamp.

#2 — stBridgeCfg / ST_LogBridgeCfg are dead Cleanup

Owner: engineering · Cosmetic but visible to operators

GVL_Log.stBridgeCfg existed solely so the retired RobotBridge/log_pump.py could publish its logger configuration (log dir, level, retention days/MB, poll ms) for an HMI to display. Nothing writes it. It reads as empty strings and zeros, and FlowerPyHmi's Logs page renders a blank "Log bridge config" block as a result.

How to resolve. Remove the field from GVL_Log, delete ST_LogBridgeCfg.TcDUT, drop BRIDGE_CFG_FIELDS + _read_bridge_cfg from FlowerPyHmi, and remove the block from its Logs template. Run python scripts/check_pyhmi_contract.py afterwards.

#3 — Parameter ranges have two sources of truth Drift risk

Owner: engineering · Nothing keeps the two in step automatically

The 11 robot parameter ranges are now enforced in three places: the panel's per-control InputBoxMin/InputBoxMax, FB_RobotTcpClient's ParamMin/ParamMax (the real backstop, since per-control limits only protect their own control), and FlowerPyHmi's ParamField.lo/hi in flower_py_hmi/robot.py.

FlowerPyHmi is a separate repo, so its copy is a second source of truth that nothing reconciles. scripts/check_pyhmi_contract.py checks that symbols resolve; it does not compare bounds.

Options. Extend the contract check to compare the two range tables, or accept the duplication and note it (FlowerPyHmi rejects out-of-range with a 400 rather than clamping silently, so the operator sees what was refused — deliberately different behaviour from the PLC, which clamps).

#4 — Reassign the push-button LEDs to functional statuses Deferred

Owner: operator preference · One-line change in MAIN.TcPOU

The three push-button LEDs are currently dumb mirrors of the raw press state (bLedPbN := bPbN) — a wiring / hardware-health diagnostic, not a status indicator. Candidates for repurposing: LED1 = cycle running, LED2 = error latched, LED3 = TCP connected.

Deferred until operator preference is known. Note the two dedicated status lamps on dOut[12..13] already cover running and error, so the case for repurposing the PB LEDs is weaker than it was before those landed.

#5 — Small residue from retired designs Cleanup

Owner: engineering · Safe to do at any time
  • WAIT_POS2 := 2 is still declared in E_MasterAutoStep but never assigned. Safe to remove once no HMI page refers to it. Its error code 2 is correspondingly unreachable.
  • FlowerPyHmi's Continuous checkboxes (on main.html and manual_control.html) now visibly revert when ticked, because MAIN forces the field FALSE every scan. Worth removing there — but that is a separate repo.
  • FlowerPyHmi's test_master_auto_continuous_toggle passes only because mock mode has no MAIN. It is a valid API-plumbing check but does not verify the behaviour its name implies.
  • RobotBridge/ could be pruned down to Client_working_example/ + its README. See that README for the file-by-file verdict.

#6 — stParams is both setpoint and actual Known limitation

Owner: engineering · Deferred — needs a second struct

A tuning-parameter edit made while the robot link is down is overwritten by the reconnect's GET_SYNC, because the same field carries both the operator's desired value and the robot's reported value. Separating desired-from-actual needs a second struct, so this is deferred.

Workaround: make parameter changes with the link up. The Robot page shows the connection state right next to the fields.

✓ Physical DI channel assignment Closed

Rewired 2026-07-27 to match the physical terminals

All eight pistons, both plate sensors, the three push-buttons + LEDs and the two status lamps are wired. GVL_IO grew to dIn[1..24] / dOut[1..16]. The push-buttons moved down to dIn[13..15] / dOut[7..9] — dIn[13] and dOut[7] being the channels freed by retiring the robot's discrete-I/O handshake — and grip + plate moved up. dIn[16] is a deliberate gap so the grip sensors start on a terminal boundary. Full table in the Configuration reference → PLC tab.

The old caveat still applies: after an AT %I* array is resized, re-verify the EtherCAT links in the System Manager — TwinCAT does not always re-attach linked variables to a resized parent array. Symptom: sensor indicators stop updating even though nothing else changed.

✓ Robot integration architecture — TCP-only Closed

2026-07-26 · FB_RobotTcpClient on TF6310 is the sole channel

The Python bridge and the discrete-I/O handshake are both retired, as are the POS1/2/3 + AUTO_STARTED/PUSH_DONE/PISTONS_ERROR frames and WAIT_POS2. docs/robot-integration-options.md is historic — it weighed four options and is kept for archaeology only; do not plan from it. The former "robot is server or client?" question closed as robot is the server, the panel dials out.

✓ Robot tuning parameters — clamped, exposed, documented Closed

2026-07-26 · was three separate open items

FB_RobotTcpClient clamps every writer that reaches the robot through it, including the bSetParam escape hatch. All 11 values are editable on the panel's Robot page with per-control min/max. ST_RobotParams now documents percentages vs milliseconds and cites global.lua for the units. The clamp writes the bounded value back into stParams — not cosmetic: leaving an out-of-range number in the field would keep it permanently different from its shadow and re-send every idle scan.

✓ Persistent data was never written to disk Closed

2026-07-27 · FB_PersistentAutoSave

PERSISTENT declares a durable storage class, not an automatic save — so every operator edit lived in RAM only and was lost on power-down, silently. A debounced flush (~2 s after editing stops) now writes it, logs each flush, and logs failures at ERR. The safety half of the same change: MAIN's cold-boot block clears bContinuous (tested as a level, so restoring it TRUE would drive pistons within one scan of power-up) while deliberately keeping bAutoMode.

✓ Continuous cycling disabled + status lamps added Closed

2026-07-27

Every cycle is started by the operator or the robot, so the AutoMain checkbox was removed and MAIN forces the field FALSE every scan — forcing rather than merely deleting the control, because a VISU page is only one of several writers. Green (dOut[12]) / red (dOut[13]) status lamps report machine state, unlike the PB LEDs.

✓ Full-machine auto sequence Closed

Landed as FB_MasterAutoCycle

Now a 15-state coordinator across all eight pistons (3 Sep, 3 Push, 2 Grip), gated by two plate sensors, with three INIT_* homing states so a piston left extended cannot collide with the arriving plate. Pair count is fixed at 3 — the uiPairCount runtime knob was removed 2026-07-12. Error codes 0/1/3–11/99.

✓ Deprecated ST_HmiRobot fields deleted Closed

2026-07-26

bAtPos1/2/3, bTx* and bRxResetError removed — nothing referenced them, and check_pyhmi_contract.py still resolved every FlowerPyHmi symbol without them. Consequence worth knowing: RobotBridge/robot_bridge.py and bridge_gui.py write these fields, so they would now fail at runtime.

✓ SOL-Spring piston migration + coil latch fix Closed

All pistons on FB_SolSpringPiston_2Pos

Single Extend coil, mechanical spring returns the piston. The Section 2 ladder is intentionally latch-and-retain (no ELSE branch) so the coil stays energised until the next command — a "clear when target reached" branch would let the spring pull the piston back mid-cycle. A later addition: one release branch (F_TRIG on bJogExtend) so panel push-button jog is momentary, positioned after both jog branches and before the target branches.
