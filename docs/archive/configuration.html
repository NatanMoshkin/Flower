System architecture

One CP6606 Panel PC is the entire control system. It runs the TwinCAT PLC (eight SOL-Spring pneumatic pistons — single Extend coil, mechanical spring returns them — over EtherCAT), the operator interface as a classic PLC visualization rendered by the PLC runtime itself, and the robot comms in native ST. Nothing else has to be running for the machine to work.

Key design choice — reversed 2026-07-26. The PLC now owns the socket. FB_RobotTcpClient is native ST on Tc2_TcpIp, and TF6310 is installed and running on the CP6606. This is the one documented exception to the project's avoid-paid-Beckhoff-supplements rule; see the memory note feedback_avoid_licensed_beckhoff_libs.
What this replaced. The Python bridge (RobotBridge/) is retired — it could never have run on the panel (Windows Embedded Compact 7 on ARM has no supported CPython, so no pyads), and the POS1/POS2/POS3 protocol it implemented was never what the robot actually speaks. The discrete-I/O handshake (STAND_SEQ_DO / STAND_SEQ_DI) is retired too; the channels it freed now carry PB1 and its LED. See RobotBridge/README.md.
Direction of the socket. The robot is the TCP server; the panel is the client and dials in at 192.168.201.1:6001. That endpoint is editable on the panel's Robot page and persists — it is a commissioning value, not a compile-time constant.

Project root: Panel_PLC_HMI/167_01_Saad_PLC/167_01_Saad_PLC/. PLC1 uses free Beckhoff libraries (Tc2_Standard, Tc2_System, Tc3_Module) plus Tc2_TcpIp, which ships with TF6310 — installed and running on the CP6606, and the one documented exception to the no-paid-supplement rule.

Function block — FB_SolSpringPiston_2Pos

One FB drives every piston instance (eight today: SepSol1..3, PushSol1..3, GripSolL, GripSolR). SOL-Spring topology: a single Extend coil, mechanical spring returns the piston when the coil is de-energised. Two limit switches (Extended and Retracted) still exist on the DI side. Sections in scan order:

  • 0a — Effective sensor merge: bSwitchExtended_eff := bSwitchExtended OR stHmi.bSimulateExtended (same for retracted).
  • 0 — HMI button latching: R_TRIG on bManCmdExtend / bManCmdRetract selects the latched target. Independent IFs — retract wins on same-cycle collision.
  • 1 — Mode → target mapping: Auto uses bAutoCmd* pins, Manual uses bSelected* latches, otherwise safe-default zeros.
  • 1a — Jog override: while either bManJog* button is held, latched selections are cleared.
  • 1b — Target-reached reset: once the piston arrives at a sensor, the corresponding latched selection is dropped.
  • 2 — Coil drive ladder (latch & retain): Jog Extend energises the coil while held (Manual-mode gated); Jog Retract de-energises. A panel push-button release branch (F_TRIG on the bJogExtend input) de-energises the coil so PB jog is momentary. Otherwise the coil is latched — once TRUE by an Extend target it stays TRUE until an explicit Retract target flips it. No ELSE branch: the mechanical spring, not the ladder, is what retracts the piston, so the coil must not drop simply because the target has been reached.
  • 3 — HMI status feedback: mirrors effective sensor + coil state into stHmi. bIsMoving := NOT bSwitchExtended_eff AND NOT bSwitchRetracted_eff.
Latch semantics matter here. A SOL-SOL piston keeps position after both coils de-energise. A SOL-Spring piston does not — if the coil drops mid-cycle the spring pulls the actuator back. The Section 2 ladder is written specifically to hold the coil high until the next command; do not "clean it up" by adding an ELSE branch that clears the coil at the target.
The PB-release branch's position in the ladder is load-bearing. It sits after both jog branches, so a held HMI bManJogExtend keeps the coil energised and the one-scan release pulse is ignored; and before the bTarget* branches, so a latched HMI Extend selection cannot re-energise the coil the moment the operator lets go of the push-button. The HMI jog deliberately keeps its latching behaviour — Extend and Retract jog sit side by side on the Piston page, so there is no stranding problem there.

Function block — FB_MasterAutoCycle

Coordinates all eight pistons — 3 Sep, 3 Push, 2 Grip — through a 15-state sequence gated by two plate sensors. Pair count is fixed at 3. Full state table in CLAUDE.md; summary:

  • IDLE (0). Wait for operator START or bExtStartPulse (MAIN's rising edge on the robot's CMD:1) or bSimStep_Idle / bSimStartAssembly. On start it goes to INIT_PUSH_RETRACTING, not straight to SEP_EXTENDING, so pistons left extended by a prior manual move are driven home first.
  • INIT_PUSH_RETRACTING (10) → INIT_SEP_RETRACTING (11) → INIT_GRIP_RETRACTING (12). Drive everything home. Each auto-satisfies on the next scan when already home.
  • WAIT_PLATE (20). Wait for bPlateSenL AND bPlateSenR. Uses its own tPlateWaitTimeoutMs, bounded by robot placement time. Sensors are latched at start only, not monitored past this step.
  • GRIP_EXTENDING (21) → SEP_EXTENDING (1) → PUSH_EXTENDING (3) → DWELL_PUSH (4) → PUSH_RETRACTING (5) → PUSH_RETRACTED_DWELL (6) → SEP_RETRACTING (7) → SEP_RETRACTED_DWELL (8) → GRIP_RETRACTING (22) → IDLE. Grip stays extended from GRIP_EXTENDING right through SEP_RETRACTED_DWELL. The cycle counter increments in GRIP_RETRACTING.
  • ERR (99). Latched. iErrorCode = the step's fault code (1, 3, 4, 5 for the four Sep/Push moves; 6, 7, 8 for the three INIT states; 9 = WAIT_PLATE timeout; 10, 11 for the two Grip states; 99 = STOP while running). Code 2 belonged to the retired WAIT_POS2. Reset on HMI RESET rising edge or the robot's CMD:2.

Master sensorless mode (stCfg.bNoSensors): the eight movement states ignore sensor feedback and advance when tStepTimeoutMs expires — the timeout doubles as the fixed step duration, so codes 1/3/4/5/6/7/8/10/11 cannot occur. WAIT_PLATE is deliberately not covered; skipping the plate gate is safety-relevant, so it needs its own explicit bBypassPlateSensors flag, which suppresses only the timeout error and keeps the wait.

Continuous cycling is disabled on the real machine (2026-07-27). The panel checkbox was removed and MAIN forces stMasterAutoCfg.bContinuous := FALSE every scan. Forcing rather than merely deleting the control matters: a VISU page is only one of several writers — FlowerPyHmi has its own Continuous checkboxes and writes the field over ADS. Removing the panel checkbox alone would have hidden the control while leaving the behaviour reachable. The field is kept in the struct because the FB clears it in six places on ERR/STOP paths.

Per-piston FB_PistonAutoCycle instances still exist and are OR-merged onto bAutoCmd* at each call site, but the panel exposes no per-piston auto tiles: in Auto the master owns all eight pistons, in Manual the master is held at IDLE.

Function block — FB_PersistentAutoSave

Called last in MAIN. Watches all nine structs in GVL_HmiPersistent plus the two GVL_Robot scalars, and flushes to Port_851.bootdata about 2 s after the operator stops editing.

Why this exists. PERSISTENT declares a durable storage class, not an automatic save. TwinCAT flushes RAM to bootdata on exactly three triggers: a clean PLC stop, an explicit FB_WritePersistentData call, or the IDE's "Save persistent data". Cutting power to a CP6606 is not a clean stop, and nothing called the FB — so every operator edit lived in RAM only and was lost on power-down, silently.
  • Two shadow sets make "stopped editing" detectable at all. shSaved = what we believe reached disk, refreshed only after a successful write (so a failed write leaves it alone and the retry happens naturally). shSeen = what we saw last scan, refreshed every scan.
  • The quiet timer runs only while dirty AND NOT changing, so it restarts on every keystroke. Debounced rather than write-on-change because the panel boots from Compact Flash — one edit of a 5-digit timeout would otherwise be five writes.
  • Comparison is MEMCMP because IEC has no struct <>. Completion is the falling edge of BUSY — FB_WritePersistentData has no DONE output.
  • Every flush logs to GVL_Log (visible on the Logs page); a failure logs at ERR severity rather than failing silently.
The safety half of this fix — do not remove one without the other. Making persistence work also makes the stMasterAutoCfg BOOLs survive a power cycle. MAIN section 0 is a cold-boot block that deals with that: bContinuous is cleared (and now forced every scan) because the FB's IDLE branch tests it as a level, so restoring it TRUE would drive pistons within one scan of power-up with nothing external gating it. bAutoMode is deliberately kept (operator decision, 2026-07-27) — the machine returns to Automatic at IDLE and still needs a real start trigger. The timers, bNoSensors and bBypassPlateSensors are not cleared either: they are operator config, and persisting them is the point. Be aware a bench flag left on now survives a reboot.

GVL_RobotTwo blocks. Volatile: stParams (ST_RobotParams), stRobot (status mirror), bTcpEnable. GVL_LogaLog[0..255] ring of ST_LogEntry + monotonic nWriteIdx, plus aRecent[0..19] newest-first mirror that the Logs page binds directly, bLogEnabled, bDebugMode, and sNow (HH:MM:SS, refreshed once a second by MAIN from FB_LocalSystemTime). F_LogEvent writes both rings.
The panel log is RAM-only. There is no file I/O anywhere in the PLC — no FB_FileOpen/FB_FilePuts, and no ADSLOGSTR, so nothing reaches the TwinCAT system event log either. GVL_Log is plain VAR_GLOBAL (not persistent), so every entry is lost on power cycle, PLC reset or download, and only the last 256 events are kept. Permanent records require FlowerPyHmi, which drains the ring into rotating files on a laptop.
Where the HMI contract lives. Four GVLs carry the {attribute 'TcHmiSymbol.AddSymbol'} pragma — GVL_HMI, GVL_HmiPersistent, GVL_Log, GVL_Robot. That pragma is the searchable marker for the whole PLC↔HMI contract; grep for it under PLC1/GVLs/. Put new HMI-facing symbols in the GVL whose concern they match — do not consolidate into GVL_HMI. After changing any of them, run python scripts/check_pyhmi_contract.py, because FlowerPyHmi is a separate repo and nothing keeps its symbol list in step automatically.

dIn[13] and dOut[7] are the channels freed by retiring the robot's discrete-I/O handshake. dIn[16] is a deliberate gap: it closes out the second 8-channel input terminal so the grip sensors start on a terminal boundary.

Tag convention: <Device>Sol<N> = a single Extend coil (SOL-Spring, spring retracts). Retract sensors still exist on the DI side — retracted-position feedback is useful even without a retract coil.

Push-button behaviour is gated by bAutoMode. In Automatic, PB1's rising edge starts a cycle and PB2/PB3 are ignored. In Manual, all three are momentary jog: held → extend, released → retract (PB1 = both Grip, PB2 = all 3 Sep, PB3 = all 3 Push). The three PB LEDs are dumb mirrors of the raw press state — a wiring/health diagnostic, not a status indicator. The two status lamps on dOut[12..13] are the real indicators: RED while latched in ERR; GREEN steady in Auto+IDLE, blinking (400 ms) in Auto+cycling, off in Manual or ERR. Green is off in ERR so the two lamps cannot contradict each other.

MAIN scan structure

Scan order in PLC1/POUs/MAIN.TcPOU. MAIN no longer touches GVL_IO — PRG_IoMap owns that on its own faster task.

  1. Section 0 — cold boot + forcing. A one-shot cold-boot block, plus stMasterAutoCfg.bContinuous := FALSE forced every scan. bAutoMode is deliberately not touched.
  2. Section 0a — clock tick. Refresh GVL_Log.sNow from FB_LocalSystemTime (dwCycle := 1), rebuilding the string only when the second rolls over. It lives in a GVL rather than inside F_LogEvent because a FUNCTION cannot own an FB instance — functions are stateless, so the cyclic tick has to happen in a POU that has one. Reads '--:--:--' until the time source reports valid, so an unset panel RTC looks like an unset clock rather than events at 00:00:03.
  3. Call fbRobotTcp. One socket, dialled out to sRobotHost:nRobotPort. Writes the status mirror and nRobotCmd; reads nStateOut and the 11 params.
  4. R_TRIG on stParams.nRobotCmd. MAIN owns the edge detection: = 1 feeds a one-scan bExtStartPulse into the master cycle, = 2 drives stMasterAuto.bReset.
  5. Call fbMasterAutoCycle. Reads bIs* from all eight piston structs and the two plate sensors. Called before the piston FBs so its command arrays feed forward this scan.
  6. Global Auto/Manual hard interlock. bAutoMode is driven unconditionally each scan onto both eMode and bMode of all eight pistons. FB_SolSpringPiston_2Pos edge-syncs the two, so forcing only one would let a stray toggle propagate for a scan; forcing both closes that gap.
  7. Compute nStateOut. Immediately after the master cycle, so any transition this scan is visible to the robot on the next STATE push. TO_INT(eStep) in Auto; the MANUAL = 30 sentinel while bAutoMode = FALSE.
  8. Call eight piston FBs. Each bAutoCmd* is an OR-merge of the per-piston auto FB and the master's array output. The panel push-buttons feed the separate bJogExtend VAR_INPUT, so MAIN never mutates the HMI-owned stHmi.bManJogExtend field.
  9. Status lamps. bLedRed := (eStep = ERR); bLedGreen steady / blinking / off per the table above. The blink source is a self-resetting TON toggling a BOOL, not TON.Q directly — a bare TON pulses for a single scan per period, which would be invisible rather than a blink.
  10. Call fbPersistentAutoSave last. Debounced flush of everything persistent.
Mode-forcing replaced the old "put all pistons to Auto on Start" checkbox. A single machine-wide bAutoMode is now the sole source of truth for every piston's mode — "no option to double control". In Auto the master cycle owns all eight pistons; in Manual it is held IDLE and the operator jogs.

Naming convention

Follows the project's TwinCAT_NamingConventions skill (Structured Hungarian):

  • b* BOOL, n* integer (UDINT/DINT/INT), r* REAL/LREAL, s* STRING, e* ENUM, st* STRUCT instance, fb* FB instance.
  • FB_* function block declaration, ST_* struct type, E_* enum type, GVL_* global variable list.
  • Signals prefixed by role: bSensor* (inputs), bValve* (outputs), bMan* (HMI-writes), bSelected*/bIs*/bOut* (FB-writes).

Panel VISU — classic PLC visualization

The operator interface is a classic TwinCAT visualization rendered by the PLC runtime on the CP6606 itself. Seven .TcVIS pages under PLC1/VISU/.

The TwinCAT web HMI is gone. Flower_PLC_HMI/ — the dev PLC solution and the TcHmi web HMI Flower_HMI/ — was deleted 2026-07-26. There is no mirror solution to keep in sync any more, so PLC edits land in one place only. The engineering-side UI is now FlowerPyHmi (separate repo at 167_01_Saad_Flower/FlowerPyHmi, ADS over the network). Everything below is about the panel's own VISU, which is a completely different technology from TcHmi: numeric-ID XML serialization, no JSON schemas, no symbol ACLs.

Editing rule — clone, never author

Do not hand-write elements into a .TcVIS. These files use numeric-ID serialization, and XAE silently drops elements it cannot parse — the file still parses as XML, the build still succeeds, and the element simply is not there. Every element in this project was produced by cloning a proven block from an existing page and retargeting it. After any edit, open the page in TcXaeShell and confirm the element renders before activating.

Run python scripts/validate_visu.py after every VISU edit. It asserts two things XML well-formedness does not give you: that each element is a direct child of VisualElementList, and that no GUID is shared between two pages.

Two identity layers, and the trap in the second

  • Each page's <Visu Id> GUID equals every VisualElementOwningObjectGuid inside it. Hold that invariant when cloning a page.
  • Besides its elements, every page carries ~60 more GUIDs naming the objects the compiler generates for it: VisuRegDesc.FbGuid, InputsPou.FbGuid (this one becomes <Page>__inp__vis), one per generated method, the generated GVLs, VisuRegisterGvl, DialogDut.

This one bit real work. GripperManual was cloned from PistonsManual and duplicated all 61 of them. Because the first FbGuid happens to equal <Visu Id>, the page-GUID rewrite fixed exactly one and the diff looked complete. Two visualizations then registered the same input POU and the build failed with Unknown type: 'PistonsManual__inp__vis' — naming a file that had not been touched in weeks. The page rendered fine throughout; only a build catches this. Fix with scripts/fix_visu_object_guids.py, which re-issues a clone's copies (uuid5-derived, so idempotent) — rewrite the clone, never the original.

The invariant, confirmed against the pristine IDE-authored pages: outside <TypeList>, no GUID is shared by any two .TcVIS files. (<TypeList> is the exception — it references VisualElem plugin types that are identical everywhere.)

A page name is an IEC identifier

The compiler generates an FB and a <Page>__inp__vis type from the page name, so it must not collide with a standard function. The Logs page was first called Log and failed to compile with Identifier expected instead of "Log" — LOG is an IEC 61131-3 standard function, as are LN, EXP, ABS, SQRT, SEL, MUX, LEN, LEFT, MID and FIND. The displayed label is unconstrained: the page is named Logs while its title and nav button both read "Log".

The classic VISU cannot stringify an enum

Treat this as settled. {attribute 'to_string'} on an enum makes TO_STRING() available in ST only — it does not teach the visualization anything. Binding aRecent[i].eSev to a text output renders 0/1/2/3. This was assumed the other way round and shipped wrong twice before being fixed on 2026-07-27.

That is why every page here carries a STRING mirror next to its enum: sStepText beside eStep, sErrorText, sConnStateText, and ST_LogEntry.sSevText beside eSev. sSevText is STRING(8) rather than an exactly-sized STRING(4) so a future severity name cannot truncate silently.

The Logs page's middle column shows Time, not Source (changed 2026-07-27). ST_LogEntry used to carry no timestamp on the reasoning that "Python assigns wall-clock time when it drains the ring" — true, but that only ever covered FlowerPyHmi; the panel has no drainer, so the page had no way to show when. sSource is untouched in the struct and still reaches FlowerPyHmi; only the panel column changed. Layout is now Sev 20-80, Time 84-174, Message 178-780.

The timestamps are only as good as the panel RTC. If FB_LocalSystemTime reports invalid, sNow reads '--:--:--' rather than a plausible wrong time — an unset clock should look unset.

Numeric entry — the one element that had to come from the IDE

The project originally had only two input mechanisms (Visu_TapInput → BOOL, and ChangeVisuInputAction), so there was nothing to clone for an editable number. The operator authored one template in TcXaeShell (GenElemInst_229 on the Robot page), and all 16 editable fields are clones of it.

The template is a plain VisuFbElemTextfield whose OnMouseClick carries an InputBoxInputAction; UseTextOutputVariable=true means it writes back through the normal displayed-variable member. So a display field and an edit field differ only by that action block — which is exactly why it could not be invented and had to come from the IDE.

  • Robot page — 11 params at x 420-770, bound to GVL_Robot.stParams.<NAME> (absolute paths: it is a standalone page). Each carries InputBoxMin/InputBoxMax at the vendor range.
  • AutoMain — 5 timers at x 500-780, bound to stCfg.<name> (interface-relative: AutoMain is embedded as a frame in Main and declares stCfg : ST_HmiMasterAutoCfg, so absolute paths would be wrong here).
  • Robot IP — a clone of the same field with format %s and InputBoxMin/InputBoxMax cleared (numeric bounds are meaningless on a STRING). InputType stays "Default", which derives the dialog from the bound variable's type — that is why a STRING gets the alphanumeric keypad and no new element type had to be authored.
Per-control limits only protect the control they are set on. The 11 params are bounded on the panel, but FlowerPyHmi, any future ADS client, and the bSetParam escape hatch all bypass them — which is why FB_RobotTcpClient clamps again on the way out (see the Robot tab).

Robot — TCP from the PLC (FB_RobotTcpClient)

Native ST in PLC1/POUs/FB_RobotTcpClient.TcPOU, using Tc2_TcpIp (ships with TF6310, installed on the CP6606). Dials the robot's server at GVL_Robot.sRobotHost:nRobotPort and keeps one persistent socket. MAIN calls it every scan.

This replaced the Python bridge. RobotBridge/ is retired: it could never have run on the panel (WinCE 7 on ARM has no supported CPython, so no pyads), and the POS1/POS2/POS3 protocol it implemented was never what the robot speaks. The discrete-I/O handshake is retired too. See RobotBridge/README.md for what is still kept there and why.

Wire protocol

Raw ASCII, NO newline framing. One send → one reply. Matches the vendor's reference client and dummy server, plus the STATE/CMD frames added for this machine.

PLC → robotRobot → PLCPurpose
GET_SYNCSYNC:NAME=VALUE,...Pull all 11 tuning params
NAME:VALUEOK: SET NAMESet one tuning param
New_Bulb:1OK: SET New_BulbStart a fresh bulb
STATE:<n>CMD:<m>State push + command receive
  • STATE:<n> — n is the INT value of E_MasterAutoStep, or MANUAL = 30 when bAutoMode = FALSE. Sent on every change of nStateOut and every IDLE_STATE_MS (default 1000 ms) as keep-alive. This replaced the old bare HEARTBEAT frame — it serves the "is the socket alive?" role while also carrying real information. The robot derives "PLC is running" from n ≠ 0.
  • CMD:<m> — 0 = none, 1 = start cycle, 2 = reset error. Written into stParams.nRobotCmd; MAIN owns the R_TRIG and feeds pulses into FB_MasterAutoCycle.bExtStartPulse or the HMI's bReset. The robot is responsible for zeroing it after the next state push acknowledges the command.

The retired POS1/POS2/POS3 + AUTO_STARTED / PUSH_DONE / PISTONS_ERROR frames are gone, as is WAIT_POS2 — the Dobot's PerformStandSequence moves the arm clear of the stand before it issues CMD:1, so no intermediate "robot moved away" wait is needed.

Connection state machine

Disconnected → Connecting → Connected → (any socket error) close + reconnect after 3 s, forever while bTcpEnable = TRUE. 2-second timeout on connect / send / recv, per Tc2_TcpIp. An empty sSrvNetId targets the local TF6310 server.

Status is mirrored into GVL_Robot.stRobot: eConnState, sConnStateText, nPacketsRx, nPacketsTx, sLastMessage, sLastTxMessage.

Changing the endpoint tears down the live session. The connect call reads sRemoteHost once, so without that an edited IP would sit in the field doing nothing until the socket happened to drop — the field would look broken. The retarget routes through the same Error close-and-retry path the disable request uses, and is baselined on the first scan so it cannot force a pointless reconnect at startup.

The 11 tuning parameters

Units are percentages for the four speeds and milliseconds for the waits — traced to the robot repo's global.lua, where Init() calls VelJ(J_SPEED) / VelL(L_SPEED) ("Joint Speed %" / "Linear Speed %") plus SpeedFactor(FACTOR_SPEED) with FACTOR_SPEED = 80 scaling everything globally. WAX_SPEED / WATER_SPEED feed the v= velocity-ratio option of MovL.

Ranges are authoritative because the vendor's own GUI clamps to them (RobotBridge/Client_working_example/tcp client.py):

ParamRangeUnit
J_SPEED, L_SPEED1–100%
WAX_SPEED, WATER_SPEED0–100%
REPEATS1–10count
START_WAIT, WATER_WAIT, STAND_WAIT, END_WAIT, WAX_WAIT_TIME_OUT10–10000ms
WAX_WAIT_TIME_IN0–10000ms
The PLC clamps every writer. ClampParam / ParamMin / ParamMax bound the panel, FlowerPyHmi over ADS, any future ADS client, and the bSetParam escape hatch (via ParamIndex reverse lookup; unknown names pass through unclamped, which is the point of an escape hatch). Nothing else in the stack enforces them — src2.lua assigns tonumber() straight through with no clamp.

Two design points worth not undoing:

  • The clamp writes the bounded value back into stParams. This is not cosmetic: the shadow is updated to the value that was sent, so leaving an out-of-range number in the field would keep it permanently different from its shadow and the FB would re-send on every idle scan — a silent packet storm. Writing back converges, and the panel then shows what the robot actually got.
  • Clamping applies only on the way out, never to values arriving in a SYNC reply. Rewriting a robot-sourced value would push our table back at the robot, and if the table were ever wrong the two ends would fight.

Read/write params — the shadow-copy push

The params used to be read-only in practice: GET_SYNC pulled values in, but the only way to push one back was the bSetParam/sSetName/nSetVal triple, which nothing ever set. An operator editing stParams.J_SPEED saw the value change, nothing was sent, and the next reconnect's GET_SYNC silently reverted it.

The FB now keeps aShadow : ARRAY[1..11] OF INT, re-baselined by SetShadowAll after every GET_SYNC round-trip. Any live field that diverges from its shadow slot is an operator edit and is pushed as NAME:VALUE, one param per round-trip. HandleReply banks the value that was sent (nPendVal), so an edit made mid-round-trip is re-sent rather than swallowed. bShadowValid gates detection until the first SYNC lands, so the compiled-in defaults are never mistaken for edits.

ParamValue / ParamName index order must match the robot's SYNC_ORDER. That order is documented by the vendor reference client. Get it wrong and values land in the wrong fields with no error anywhere.

IO_IDLE priority order — asserted by the tests

  1. Post-connect one-shot GET_SYNC — a STATE reply can carry CMD:1, and a cycle must not start on unsynced params.
  2. STATE on change — CMD frames ride back on STATE replies, so a write burst must not starve start/reset.
  3. Explicit bSetParam / bTriggerNewBulb / bGetSync.
  4. Detected edits.
  5. STATE keep-alive.

scripts/test_param_shadow_logic.py ports the sequencer to Python and runs it against the protocol (9 cases: no startup echo, edit pushed, all three speeds, state preemption, CMD during write burst, mid-flight re-edit, escape hatch, re-sync baseline, malformed SYNC). It validates the algorithm, not the ST build — a TwinCAT compile is still required.

Known limitation. stParams is both setpoint and actual, so an edit made while the link is down is overwritten by the reconnect's GET_SYNC. Separating desired-from-actual needs a second struct — deferred.

Bench testing without a robot

Use FlowerPyHmi/tools/dummy_server_tcp.py --allow-commands. It implements the full current protocol including the STATE / CMD frames. Point the panel at the laptop by editing the IP on the Robot page — no rebuild needed, and the value persists.

RobotBridge/Client_working_example/dummy_server.py predates the STATE/CMD frames and only covers GET_SYNC / NAME:VALUE; keep it as a statement of the vendor's own server semantics, not as a test tool.

Licensing rationale — revised

The project's standing rule is to avoid paid Beckhoff supplements: TF6100 (OPC UA server) and TF6701 (MQTT / Tc3_IoT_Communicator) remain off-limits.

TF6310 is the documented exception. It is installed and running on the CP6606, which makes Tc2_TcpIp free to use here and lets the PLC own the socket directly. That is what made the Python bridge unnecessary — and since the bridge could not have run on the panel anyway, avoiding TF6310 would have meant permanently depending on a laptop being plugged in. See the memory note feedback_avoid_licensed_beckhoff_libs for the durable version of the rule and this exception.
