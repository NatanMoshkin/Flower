Install

First-time setup. In production the CP6606 panel is the entire control system — PLC runtime, operator VISU and robot comms all on one ARM device. Nothing else needs to be running. A developer laptop is needed only to build and activate, and optionally to run FlowerPyHmi.

Prerequisites

  • TwinCAT 3.1 (build 4026 or newer) with the TcXaeShell IDE, on the engineering laptop.
  • TF6310 TCP/IP — installed and licensed on the CP6606. Required: FB_RobotTcpClient uses Tc2_TcpIp.
  • Python 3.9+ on the laptop — only for the scripts/ helpers and FlowerPyHmi. Not needed on the panel, and not installable there.
  • Git.
This reverses the old rule. Earlier versions of this guide said TF6310 was not installed and must not be referenced. That is no longer true and has not been since 2026-07-26 — TF6310 is the one documented exception to the avoid-paid-supplements rule, and the PLC now owns the robot socket directly. TF6100 (OPC UA) and TF6701 (MQTT) are still off-limits.
TE2000 TwinCAT HMI Engineering is no longer needed. The web HMI was deleted 2026-07-26. The operator UI is the classic PLC visualization, which is authored inside the PLC project in TcXaeShell.

1. PLC — build & activate

  1. Open Panel_PLC_HMI/167_01_Saad_PLC/167_01_Saad_PLC.sln in TcXaeShell. This is the only PLC solution — the former dev mirror Flower_PLC_HMI/ was deleted, so there is nothing to keep in sync.
  2. Build → Build Solution. Zero errors expected.
  3. TwinCAT → Activate Configuration. Restart the runtime in Run mode when prompted.
  4. Verify: PLC → Login, then confirm GVL_Robot.stRobot is present and GVL_Robot.sRobotHost holds the expected address.
If the project appears unloaded in Solution Explorer — POUs missing from the tree, no Login button on the toolbar — suspect a stripped .tsproj commit. Check git diff for a massive line reduction in .tsproj; that file is IDE-owned and must not be hand-edited.

2. Panel VISU — nothing separate to publish

The seven .TcVIS pages are part of the PLC project and deploy with it. There is no separate build or publish step, no web server, and no login.

  1. Confirm each page is registered in PLC1.plcproj with a <Compile Include> + <DependentUpon> block. An unregistered .TcVIS is invisible to the build.
  2. Run python scripts/validate_visu.py — asserts element parentage and that no GUID is shared between pages.
  3. Open each page in TcXaeShell and confirm every element renders. XAE silently drops elements it cannot parse, so this visual check is the only reliable gate.
Build error naming a .TcVIS you never touched? That file is usually the victim, not the cause — a cloned page duplicated its generated-object GUIDs. See Unknown type: '<Page>__inp__vis' in the Configuration reference's Panel VISU tab, and fix with scripts/fix_visu_object_guids.py on the clone.

3. Robot endpoint — no config file

The robot's address lives in the PLC as GVL_Robot.sRobotHost / .nRobotPort (factory default 192.168.201.1:6001), declared in a VAR_GLOBAL PERSISTENT block and editable on the panel's Robot page. There is no YAML, no config.yaml, and no service to restart.

Why they must be persistent. The test for configuration is "does the correct value differ between installations?", not "does it reset on boot?". As plain VAR_GLOBAL they were re-applied from their literals on every Activate, download and reset, silently discarding whatever was typed on the Robot page — and nothing reported an error: the write succeeded, the field really did change, and it really was reverted.

bTcpEnable is deliberately not persistent: a link disabled for a bench session comes back enabled after a restart, so the robot can never be left unreachable for no visible reason.

4. CP6606 panel bring-up

The CP6606-0001-0020 is one ARM Cortex A8 device under Windows Embedded Compact 7, running the TwinCAT PLC runtime and the operator VISU on its 7-inch 800×480 touchscreen. There is no browser and no TcHmiSrv on it. The operator UI is Beckhoff's TC3 PLC HMI, rendering the visualizations authored inside the PLC project.

  1. Add an ADS route to the panel — TcXaeShell → SYSTEM → Routes → Add Route → search the LAN, pick the CP6606, log in with the panel's user (default: no password on Beckhoff CE). Routes must be present on both sides.
  2. Set the target system — the TwinCAT toolbar's target dropdown → pick the CP6606's AMS Net ID.
  3. Enable the SVG→BMP setting — Solution Explorer under PLC1 → double-click Visualization Manager → Settings → check "Automatically convert SVG to BMP". The CE renderer does not support SVG; set this even if you ship no SVG icons today.
  4. Confirm TF6310 is installed and running on the panel, otherwise Tc2_TcpIp resolves at build time but the socket never opens at runtime.
  5. Build + Activate Configuration — writes boot files to \Hard Disk\TwinCAT\3.1\Boot\. Confirm the PLC comes up in Run mode.
  6. Configure Startup Manager on the panel — CE desktop → Start → StartMan → Startup Options → Autostart → add: Type Application, Delay 30 s (waits for the runtime to reach Run), Command \Hard Disk\TwinCAT\3.1\Components\Plc\Tc3PlcHmi\Tc3PlcHmi.exe.
  7. Reboot. After the delay Tc3PlcHmi.exe should come up fullscreen on Main, with touch navigation to the subpages working.
  8. Set the panel's clock. Log timestamps come from the panel RTC; if it is unset the Logs page reads --:--:--.
Tc3PlcHmi.ini has moved between TwinCAT builds. C:\TwinCAT\3.1\Components\Plc\Tc3PlcHmi (builds < 4022) → C:\TwinCAT\3.1\Boot\Plc (4022–4025) → C:\ProgramData\Beckhoff\TwinCAT\3.1\Boot\Plc\Tc3PlcHmi (4026+). Check the panel's build first (TwinCAT tray → About).

5. FlowerPyHmi (optional, engineering only)

Separate repo at 167_01_Saad_Flower/FlowerPyHmi. Runs on any developer laptop and talks ADS to the panel. Not required for production.

cd FlowerPyHmi
python -m venv .venv && .venv\Scripts\pip install -e .
# set plc.ams_net_id in config.yaml to the panel's AMS Net ID
.venv\Scripts\python run.py        # serves http://127.0.0.1:8000
It is not a submodule, so nothing keeps its symbol contract in step. After changing any HMI-facing GVL or DUT in the PLC, run python scripts/check_pyhmi_contract.py from the Flower repo.

6. Docs (this site)

Double-click scripts\serve-docs.bat. Serves the repo root on http://127.0.0.1:8765 and opens /docs/index.html. Leave the console open while browsing; Ctrl+C to stop. The markdown viewer needs HTTP — browsers block fetch() under file://.

Startup order

In production there is only one thing to start: the panel. Everything below is verification.

Daily startup checklist

  1. Power on the cabinet. The TwinCAT runtime and Tc3PlcHmi.exe both autostart; the panel should land on Main.
  2. Check the status lamps. Green steady = Automatic and IDLE. Green off with red lit = latched error. Green off with red off = Manual.
  3. Main screen — step reads IDLE, error code 0, error text empty.
  4. Plate lamps — the L / R indicators should match the physical state of the stand.
  5. Pistons Manual + Gripper Manual — every piston's indicators consistent with its physical state (all retracted at power-on).
  6. Robot page — state Connected, Rx and Tx counters both advancing (the keep-alive runs about once a second).
  7. Enable the robot on the Dobot pendant.
Automatic survives a power cycle by design. The machine comes back in the mode it was left in, at IDLE, still needing a real start trigger — but a robot that is already running can request a cycle immediately after power-up. That is the intended production behaviour (resume without re-arming the panel). Continuous cycling never survives: it is forced off every scan.
Check the two bypass flags before a production run. No sensors (timed steps) and Bypass plate sensors are persistent, so a bench flag left on yesterday is still on today.

What each state on the Robot page means

StateMeaningWhat to do
DisconnectedNo socket. Either bTcpEnable is FALSE or the last attempt failed.Wait 3 s — it re-dials automatically. If it stays here, check the IP field and the network.
ConnectingDialling out; 2-second timeout.Normal for a moment. Persistent = wrong address, or the robot's server is not listening.
ConnectedSocket up. Counters advancing.Nothing.
ErrorSocket error, or a requested endpoint change / disable is being applied.Transient — it routes through the close-and-retry path. Persistent = investigate the link.

Tx advancing while Rx stays flat means the robot is receiving but not replying — look at Last Tx to see what the panel last sent.

Smoke test

A. Robot link, against a simulated robot

Use FlowerPyHmi's simulator on the laptop — it implements the full current protocol including STATE / CMD:

cd FlowerPyHmi
.venv\Scripts\python tools\dummy_server_tcp.py --allow-commands
  1. On the panel's Robot page, set the IP to the laptop's address. The change takes effect immediately — the PLC tears down the live session and re-dials.
  2. Expect state → Connecting → Connected, and both counters to start advancing within about a second.
  3. Press Get Sync. The simulator logs GET_SYNC; the 11 parameter fields fill in from its reply.
  4. Edit one parameter — say J_SPEED. The panel pushes J_SPEED:<value> on the next round-trip, one parameter at a time.
  5. Enter an out-of-range value. It is clamped to the vendor range, the clamped number is what gets sent, and the field updates to show it. If the field kept the out-of-range number it would differ from its shadow forever and the FB would re-send every idle scan — a silent packet storm.
  6. Have the simulator send CMD:1. In Automatic at IDLE, a cycle starts. Send CMD:2 while latched in ERR — the error clears.
  7. Press New Bulb. The simulator logs New_Bulb:1.
Do not use RobotBridge/ for this. sim_robot.py and sim_robot_server.py speak the retired POS / AUTO_STARTED protocol, and robot_bridge.py / bridge_gui.py write PLC fields that no longer exist — they would fail at runtime.

B. Protocol-level check without a PLC

The state sequencer is ported to Python, so the priority chain can be tested without a TwinCAT compile:

python scripts/test_param_shadow_logic.py

Nine cases: no startup echo, edit pushed, all three speeds, state preemption, CMD during a write burst, mid-flight re-edit, escape hatch, re-sync baseline, malformed SYNC. It validates the algorithm, not the ST build — a TwinCAT compile is still required.

C. Piston moves, independent of the robot

  1. Untick Auto Mode on the Main screen. The master cycle is now held at IDLE.
  2. Pistons Manual → Extend on SepSol1. Confirm the coil indicator lights and the Extended sensor arrives.
  3. Hold PB2 — all three Sep pistons extend. Release — they retract. Repeat with PB3 (Push) and PB1 (both Grip).
  4. Confirm each push-button's LED lights while pressed. The LEDs are dumb press mirrors, so this is a wiring check.
  5. Tick Auto Mode, press START, and watch the step walk the 15-state sequence. The three INIT_* states should satisfy immediately if everything is already home.
  6. Confirm the green lamp blinks while cycling and returns to steady at IDLE, and that the cycle counter incremented.
No plate on the stand? The cycle will sit in WAIT_PLATE and raise error 9 after tPlateWaitTimeoutMs. Tick Bypass plate sensors to turn that timeout into a fixed dwell and let the cycle continue — but untick it before production.

D. Persistence

  1. Change a timer on the Main screen — say Dwell PUSH to 1500.
  2. Wait about 3 seconds. The flush is debounced ~2 s after the last keystroke.
  3. Check the Log page — a flush entry should appear. A failure logs at ERR severity.
  4. Power-cycle the panel. The value should come back as 1500.
If you power off within ~2 s of typing, the edit is lost — that is the debounce, not a bug. Watch for the log entry before cutting power.

Recovery

Robot link will not come up

  1. Robot page → check the IP field. It persists, so it may hold a bench address someone typed last week.
  2. Confirm the robot's server is actually listening on port 6001 — the robot is the server, the panel dials out.
  3. Confirm TF6310 is running on the panel. Without it, Tc2_TcpIp builds fine but the socket never opens.
  4. Check bTcpEnable. It is not persistent, so a restart re-enables it.
  5. Last Tx / Last Rx on the Robot page are the fastest diagnostic — they show the actual frames.

A persistent value reverted

  • Within ~2 s of the edit? The debounced flush had not fired. Expected.
  • After an Activate Configuration or download? Expected for anything not declared persistent. If it is a robot endpoint, confirm it is still in GVL_Robot's PERSISTENT block.
  • Was it Continuous? That one never persists — it is forced off every scan, deliberately.
  • Did a struct change shape? Adding or removing a field can invalidate the stored bootdata. Re-enter the values.
  • Check the Log page for a failed-flush ERR entry.

The panel log is empty

Expected after any restart — the log is RAM-only. There is no file I/O in the PLC and GVL_Log is not persistent, so every entry is lost on power cycle, PLC reset or download, and only the last 256 events are kept internally. Connect FlowerPyHmi if you need a durable record; it drains the ring into rotating files on the laptop.

Also check that Enabled is ticked on the Logs page — it is a global mute.

FlowerPyHmi shows stale, missing or empty data

  • HMI_ADS_E_INVALID_SYMBOL / symbol-not-found for a field that exists in the PLC source — the symbol table is stale. An Online Change is not always enough; a full Activate Configuration rebuilds it, and occasionally an IDE restart is the only fix.
  • A field reads fine individually but breaks a batch read — one malformed symbol-info entry fails the whole sum-up transaction, taking down every symbol in the poll cycle, not just that one. Currently known for GVL_Log.aRecent[i].sTime; needs a full Activate on the panel.
  • Everything lags or the page freezes — see the pyads_Batch_Read_Diagnostics skill. Run python tools/ads_diagnose.py from the FlowerPyHmi repo first; a healthy batch on a fresh connection while the running server crawls means the server's aged connection is the problem, not the symbol list.
  • A Continuous checkbox reverts when ticked — correct behaviour. The PLC forces the field FALSE every scan.

A VISU element vanished after an edit

XAE silently dropped it. The file still parses, the build still succeeds, the element is simply gone. Run python scripts/validate_visu.py, then re-derive the element by cloning a proven block rather than hand-authoring one. Never hand-edit .TcVIS XML.

Restoring defaults

Cold Reset from TcXaeShell wipes persistent memory and reboots the PLC — every timer, flag, and the robot endpoint return to their declared defaults. Note the robot's IP before doing this if the installation does not use 192.168.201.1.
