The rule that makes per-step pause safe: hold at the step boundary

Pause does not freeze the machine wherever it happens to be. It is requested on the PB2 press and takes effect the moment the current step's exit guard is satisfied — the machine simply does not advance. One extra term per state:

IF <exit guard> AND NOT bPause THEN advance

Because the guard is satisfied, every motion that step commanded has already completed and been sensor-confirmed. Nothing is ever held mid-stroke. That matters because all eight actuators are FB_SolSpringPiston_2Pos — single coil, spring return, no mid-position capability and no brake. A naive freeze could not have stopped a stroke anyway; this design does not need to.

Worst-case latency is therefore one step, not one bulb — typically well under a second, or the remainder of a dwell.

The timer is the trap

Nine states run tStepTimeoutMs (default 10 s). Hold a state with its timer running and the machine faults in ten seconds with an error code that lies — PUSH_EXTENDING timed out when in fact the operator paused. So a pause must drive tonStep(IN := FALSE).

Conveniently that is also the right behaviour: a TON resets its elapsed time when IN goes FALSE rather than holding it, so Continue gives the step its full timeout budget again. No snapshot-and-restore machinery is needed. The only casualty is tElapsedS reading 0.0 while paused; a separate timer would be needed to show "how long paused".

Second-order benefit: with the timer stopped, a fault cannot originate while paused at all — every PLC-detected fault in this FB is a timeout branch. The whole "paused for three minutes, came back to a spurious timeout" class disappears rather than being handled.

Two hold points that need a decision

StateConcernSuggested
DWELL_PUSH The guard is "dwell elapsed", so a pause here holds full pin load on the bulb assembly indefinitely. The 2 s squeeze becomes unbounded. Either exclude this one state from pause (advance to PUSH_RETRACTING and hold there instead — one step later, and push is then home), or cap the hold and auto-continue. Excluding is simpler and loses almost nothing.
PUSH_EXTENDING Pins fully driven, coils held. Mechanically at a hard stop so it is not a runaway, but it is the same sustained-force question one step earlier. Safe to allow. If a jam is what made the operator reach for Pause, note that the guard will not be satisfied — so the pause simply never takes effect and the step times out into ERR as it does today. That is correct behaviour, but it must be explained to operators or Pause will look broken exactly when they need it.
the retract chain Pausing between links leaves the machine part-homed — each group at a confirmed limit, nothing loaded, but not "home". Allow. Nothing is in motion and nothing is clamped. Worth showing distinctly on the panel so it is not mistaken for a completed home.

The one case where Pause cannot help

Pause waits for the exit guard. If the guard is never satisfied — a jammed piston, a sensor that never makes — then the pause never takes effect and the step times out into ERR on schedule. Pause is not an abort. The abort is STOP, which disarms immediately from any state, and from ERR the manual commands are live so the jam can be freed by hand.

What the robot is told

eStep keeps holding the interrupted step, so the wire value must come from an override in MAIN's nStateOut computation, not from writing eStep:

ConditionnStateOut
NOT bAutoMode30 (MANUAL)
paused (any step) 41 (PAUSED) ← new
otherwiseTO_INT(eStep)

Three reasons for that seam. eStep keeps meaning “where in the sequence we are”, so Continue is a single flag clear and the transition log keeps showing real steps. Nothing needs a resume variable. And there is already precedent one line above — the MANUAL = 30 sentinel is reported exactly this way and is likewise never assigned to eStep.

In practice most paused steps already report a value the robot treats as “wait”, so the override only strictly matters for IDLE. Reporting 41 for all of them anyway is what makes a paused machine visible as paused rather than as merely busy.

Reporting anything else breaks the machine

0 (IDLE) — the robot reads “armed”, sends CMD:1 within a second, MAIN consumes-and-clears it, and the request is re-asserted forever: the July 28 deadlock shape, inverted.

99 (ERR) — the robot answers CMD:2, MAIN turns it into bReset, and the robot un-pauses the machine by homing it about a second after the operator paused, with the red lamp showing a fault that does not exist.

40 (NOT_HOMED) — robot-correct but panel-wrong: green goes out and PB3 starts its blink-to-arm prompt, telling the operator to press START on a machine that is armed and merely held.

STATE:<n>Robot repliesMeaning
0CMD:1armed — start one bulb
99CMD:2faulted — reset it
anything elseCMD:0wait

That last row is why adding a state is nearly free — any value the robot does not recognise falls into “wait”, the safe default — and why renumbering one is not. It is also why NOT_HOMED = 40 needed no robot-side change when it was introduced.

Still a partition rather than a priority scheme: the jog condition and the pause condition are Boolean complements over the same two variables, so overlap is impossible by construction. PB3 already carries this identical split.

Edge-toggle, not hold-to-pause: you pause in order to walk away, hold-to-pause would collide with the same physical grip that jogs separators in Manual, and a level pause would restart the step's timeout budget on every release.

The blink→steady distinction is what makes the wait honest — without it an operator whose step has not finished yet presses again and cancels their own pause. And green is currently steady in IDLE, so a paused machine would show steady green contradicting LED2: green should be off while paused.

Rules that keep it safe

RuleWhy
The flag lives in GVL_HMI — never in GVL_HmiPersistent The biggest risk in the feature is a pause that outlives the physical state it was taken in. Every spring-return piston retracts on power loss, guaranteed, and the plate is released — so a persisted pause would resume a step whose assumptions are all void. Plain VAR_GLOBAL scrubs it on every cold boot and download, so the machine returns un-armed and un-paused for free.
STOP clears it STOP's whole point is a state only a human START leaves. A pause surviving STOP means the operator STOPs, presses START, and the machine homes and then sits paused.
Manual re-park clears it In Manual PB2 reverts to the Sep jog, so a surviving flag would be unreachable from the panel.
Entering ERR clears it Makes RESET-while-paused a non-question, in one site rather than eleven.
START clears it START means “home and arm”; emerging from the retract chain still paused is incoherent. Also a second way out if LED2 has failed.
Rejected from NOT_HOMED and ERR Nothing is driven in either, and PB2 is a manual jog in both.
No manual commands while paused Pause holds a specific coil pattern; letting the operator jog would fight it and change the physical state the resumed step assumes. STOP first if hands-on work is needed — that reaches NOT_HOMED, where manual is allowed.

One thing Pause is not

Nothing here de-energises anything. Coils are held, the plate stays clamped, and in CHECK_PLATE the robot arm may still be moving in the fixture. Pause is a process control, not a safety function, and must not be labelled, lamped or trained as one.
